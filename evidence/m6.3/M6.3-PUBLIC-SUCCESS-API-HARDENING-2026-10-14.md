## 2. Exact API behaviour changes (`qad/m6/ledger.py`, **+45/−1**)

`git diff e10e3ad..fa449cd -- qad/m6/ledger.py` contains ONLY the two guards and their docstrings.

1. **`DeepResearchRunLedgerStore.append_attempt`** — after the existing outcome normalization,
   a normalized `SUCCESS` outcome is rejected with a typed `LedgerValidationError` whose message
   names `finalize_success_attempt_atomic(...)`. The guard sits **before `self._connect()`**, so a
   refused call opens no connection: **zero** attempt rows, **zero** audit events, **zero** terminal
   mutations. Both `outcome=TerminalStatus.SUCCESS` and `outcome="SUCCESS"` are refused.
2. **`DeepResearchRunLedgerStore.terminalize`** — after the existing `TerminalStatus(...)`
   normalization, `status is TerminalStatus.SUCCESS` is rejected the same way. A non-empty
   `result_sha256` / `result_artifact_ref` does **not** bypass it (the guard runs before those
   parameters are used). No connection is opened on rejection.

**Preserved exactly (not redesigned, not weakened):** `finalize_success_attempt_atomic` keeps its
transaction architecture (one `BEGIN IMMEDIATE`, run existence, mutable/non-terminal check,
candidate-disposition completeness, exact final SUCCESS attempt, exact terminal SUCCESS result-hash
binding, both audit events, one `COMMIT`, full `ROLLBACK`) and keeps using the **private**
transactional helpers — it is **not** routed through the newly restricted public methods and there is
no second atomic-success implementation. `_require_mutable` is unchanged. Non-SUCCESS append and
terminalize behaviour, telemetry truthfulness, append-only semantics, attempt identity/ordering,
retry modes, event semantics and typed failure semantics are untouched.

**No schema expansion or migration.** The reviewer read the live SQLite schema directly (Probe 11):
`ledger_attempt` columns are exactly
`ledger_id, attempt_number, retry_mode, provider_surface, transport_type, started_at, completed_at,
outcome, error, telemetry_json` — **no result-hash/result-ref column**; `ledger_terminal` retains both
binding columns; the table set is the six ledger tables (+ SQLite-internal `sqlite_sequence`); the
trigger set is exactly the pre-existing 20 triggers; no migration-named file exists under `qad/`; the
canonical schema registry and `CANONICAL_SCHEMA_COUNT` both report **68**.
