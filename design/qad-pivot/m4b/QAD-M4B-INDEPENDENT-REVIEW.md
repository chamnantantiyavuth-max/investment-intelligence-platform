## 1. Type A and Type B Remain Separate

**Finding: ✅ SEPARATION MAINTAINED**

The Evaluation Contract (§1) defines two distinct evaluation typologies:

| Dimension | Type A | Type B |
|-----------|--------|--------|
| **Question** | Company discovered → research wrong | Material company never discovered |
| **Evaluates** | Research quality, analytical correctness, process compliance | Discovery recall, universe coverage, signal detection |
| **Fixtures** | All 10 fixture types | Industry/Company Shock, Temporary, Structural |
| **Metrics** | 28 (Evidence + Analytical + Financial + Process) + 4 EIV | 10 Discovery Quality |
| **PIT snapshots** | Different per-fixture context | Different per-fixture context |

**Evidence:**
- Evaluation Contract §1 explicitly states: *"These two types are evaluated separately with different PIT snapshots, different fixtures, and different metrics. A single evaluation score must never combine Type A and Type B."*
- Acceptance Matrix clearly labels every metric with either `| A |`, `| B |`, or `| A+B |` (shared cost metrics only) — no ambiguous assignments.
- The Closeout document lists Type A and Type B in separate dimension tables.
- **No metric in the Acceptance Matrix (44 total) spans both types** except the 6 Cost/Model Routing metrics (7.1–7.6), which are correctly flagged as `A+B` — they measure cross-cutting cost efficiency.

**Risk:** The shared cost metrics (A+B) could be misinterpreted if an evaluator sums across Type A and Type B without weighting. Recommendation: the Calibration Report should define whether cost metrics are evaluated per-type or pooled.

## 2. Fixture Lifecycle Prevents AI Labels from Becoming Ground Truth

**Finding: ✅ LIFECYCLE DESIGN IS SOUND; RISK IS ADDRESSED BUT NOT FULLY ELIMINATED**

The Fixture Lifecycle per Evaluation Contract §3.3:

```
DRAFT → REVIEWED → SEALED → (used in evaluation) → ARCHIVED
```

**Protections built into the design:**

1. **Sealing is irreversible without re-sealing.** Per §3.3: *"Once sealed, they cannot be modified without re-sealing."* This means an AI-generated label cannot be retroactively injected into a sealed fixture.

2. **Labels are pre-sealed by human curators.** The Expected Quality State, Expected Impairment, and Expected Verdict fields in each fixture spec were authored as part of the fixture design — not generated by any AI. Each fixture spec shows explicit, hand-authored label assignments (e.g., `VERIFIED`, `FAILED`, `PROBABLE`, `UNRESOLVED`).

3. **Known outcome windows provide objective ground truth.** Every fixture has a `known_outcome_window` field (e.g., `[2021-01-01, 2022-12-31]`) with real-world observable outcomes against which labels are validated.

4. **PIT enforcement prevents label leakage.** Post-AS_OF evidence is blocked by the PIT lock (proven executable in `pit-leakage-proof.py`), meaning the sealed label cannot be influenced by future information.

5. **Seal integrity is hash-verified.** The `pit-leakage-proof.py` TEST 7 proves that any mutation to the sealed source set results in `INVALIDATE SEAL`.

**Remaining risk:** The lifecycle does not explicitly address what happens if the *human curator's* label is later found wrong during calibration. The ARCHIVED state implies permanent immutability, but a label error would only be discovered during the Calibration Report (§8.2). The Evaluation Contract does not define an ERRATA or REVOKE state for curator errors. **Recommendation:** Add a `CORRECTED` lifecycle state (between ARCHIVED and a new `SUPERSEDED` terminal state) to handle curator label errors discovered during calibration, with a clear audit trail for what changed and why.

## 4. Decision-Changing Evidence Recall Is Operationally Measurable

**Finding: ✅ MEASURABLE — WITH METHODOLOGY NOTES**

**Definition (Acceptance Matrix §1.6):**
> *"% of evidence items that would change the verdict that were actually captured by the system"*

**Measurement Method:**
> *"Outcome analysis: curator designs 'verdict-altering' evidence items per fixture; system is evaluated on whether these are in the research output"*

**Operational assessment:**

| Dimension | Assessment |
|-----------|------------|
| **Pre-requisite identification** | Measurable. Curator pre-identifies verdict-altering evidence per fixture before evaluation. The fixture spec defines expected hypotheses (H1–H5) and expected verdicts — curator maps from hypotheses to specific verdict-altering evidence items. |
| **System output scanning** | Measurable. The Acceptance Matrix specifies automated/audit checks throughout; scanning for specific evidence IDs in research output is technically tractable. |
| **Weighting** | The matrix weights high-evidence fixtures (FIX-002, FIX-004, FIX-008) — this is appropriate but the weighting formula is not specified. Could introduce measurement bias if weights are not calibrated. |

**Issues identified:**
1. **No explicit verdict-altering evidence catalog per fixture.** The fixture specs list "evidence allowed" as categories (e.g., "Pre-COVID financials FY2015–FY2019") rather than discrete evidence items that could be tagged as verdict-altering. The curator needs to create this catalog as a separate deliverable before evaluation.
2. **Decision-Changing Evidence Recall could be gamed** if the system over-cites evidence but the recall measurement counts only presence, not analytical use. The metric should be paired with **Decision-Changing Evidence Utilization** (did the system *use* the evidence in its reasoning, not just cite it).
3. **No minimum recall floor vs precision tradeoff defined.** A system that cites every piece of evidence in the universe achieves 100% recall but zero precision. The current design does not bound this.

**Recommendation:** Pair this metric with a Precision-at-k or Evidence-Utility ratio to prevent recall-over-precision gaming.

## 5. Decision-Changing Candidate Recall Is Operationally Measurable

**Finding: ✅ MEASURABLE — WITH METHODOLOGY NOTES**

**Definition (Acceptance Matrix §5.10):**
> *"% of candidates in the universe that would have changed a portfolio-relevant decision (add, avoid, position size, sell) that the system discovered"*

**Measurement Method:**
> *"Outcome analysis: curator defines 'decision-important' candidates per universe; system recall against this list is the headline Type B metric"*

**Operational assessment:**

| Dimension | Assessment |
|-----------|------------|
| **Universe definition** | Measurable. Fixtures define explicit universes: FIX-006 scans all oil & gas peers, FIX-010 scans large-cap tech. The universe is bounded and enumerable. |
| **Decision-important candidate identification** | Measurable but subjective. The curator pre-identifies candidates; the measurement depends on curator judgment. Cross-validation (multiple curators independently identifying decision-important candidates) would improve reliability. |
| **Headline metric status** | The metric is correctly designated as the headline Type B metric. It maps directly to the Type B failure: "material company never discovered." |

**Issues identified:**
1. **Decision-importance is context-dependent.** A candidate may be decision-important for a long-only portfolio but irrelevant for a long/short strategy. The fixture spec does not define the assumed portfolio context. **Recommendation:** Define the assumed investment mandate (long-only quality-oriented, with ±X% position limits) in the Calibration Report.
2. **Inter-curator reliability risk.** Different curators may identify different "decision-important" candidates. **Recommendation:** Use 3-curator consensus for the baseline list, with Fleiss' kappa reported as a methodology quality metric.
3. **The metric is all-or-nothing per candidate.** There is no partial-credit mechanism for a candidate that is discovered late or with incomplete analysis. Consider a time-weighted recall (how early was the candidate discovered relative to the decision-relevant date).

## 6. Radar Incremental-Recall Design Is Unbiased

**Finding: ✅ DESIGN IS NEUTRAL — MINOR STRUCTURAL CONCERN**

**Design (Evaluation Contract §5):**
```
QAD Discovery without Radar
    vs
QAD Discovery + Radar
```

**Assessment:**

| Dimension | Assessment |
|-----------|------------|
| **Control group** | Fair. QAD-only serves as the control, Radar-augmented as the treatment. This is a standard A/B design. |
| **Measurement** | Three output categories: (1) signals by both; (2) signals by QAD only; (3) signals by Radar only. Each can be evaluated for materiality. This is unbiased — it does not pre-suppose which lane is superior. |
| **Recommendation rule** | §5.4 explicitly prevents premature retirement: *"Do NOT retire Radar in M4B. Retirement/absorption requires later evidence and Founder decision."* This prevents a false-negative result (M4B inconclusive → Radar prematurely killed). |
| **Cost measurement** | *"Incremental cost per Radar-only signal"* is measured. This is critical because Radar may discover unique signals but at disproportionate cost. The design correctly couples recall analysis with cost analysis. |

**Structural concern — lane dependency:**
QAD automated discovery lanes A + B may already incorporate some Radar-like signals (e.g., price dislocation detection, news monitoring). The comparison is only clean if the QAD-only baseline excludes any Radar-derived signals. The Evaluation Contract does not specify how lane overlap is detected and de-duplicated. **Recommendation:** Add a lane-dependency matrix to the Discovery Recall Evaluation deliverable showing which signal types can originate from which lanes, with explicit de-duplication rules.

## 7. Temporary / Structural / Mixed / False-Quality Coverage Is Sufficient

**Finding: ✅ COVERAGE IS SUFFICIENT FOR M4B**

The 10 fixture types cover the following impairment-quality space:

| Fixture | Impairment Type | Quality Assessment | Red Team Value |
|---------|----------------|-------------------|----------------|
| FIX-001 TEMPORARY | Temporary | Verified (genuine quality) | Tests optimism anchoring — system must not over-panic |
| FIX-002 STRUCTURAL | Structural | Failed (quality destroyed) | Tests denial — system must not hope for recovery |
| FIX-003 MIXED | Mixed | Probable (partial quality) | Tests binary thinking — system must segment |
| FIX-004 FALSE_QUALITY | Structural | Failed (never was quality) | Tests credulity — system must detect fraud signals |
| FIX-005 BALANCE_SHEET | Mostly-Temporary | Verified (quality, but leveraged) | Tests capital-structure blindness |
| FIX-006 INDUSTRY_SHOCK | Temporary / Cyclical | Verified (industry leader) | Tests industry-vs-company conflation |
| FIX-007 COMPANY_SHOCK | Mostly-Temporary | Probable (quality damaged but intact) | Tests event-vs-structure confusion |
| FIX-008 AMBIGUOUS | Unresolved | Unresolved | Tests forced verdict bias |
| FIX-009 VALUATION_FAILURE | Temporary | Verified (quality intact) | Tests price-fundamental separation |
| FIX-010 NARRATIVE_PANIC | Mostly-Temporary | Verified (quality clearly intact) | Tests narrative resistance |

**Coverage assessment:**
- **Temporary impairments:** 5 fixtures (1, 5, 6, 7, 9 — covering true temp, balance-sheet, industry, company, valuation)
- **Structural impairments:** 3 fixtures (2, 3, 4 — covering pure structural, mixed, false quality)
- **Ambiguous:** 1 fixture (8)
- **Narrative/panic:** 1 fixture (10)
- **False-quality:** 1 dedicated fixture (4), cross-tested by 2 and 8

This coverage is sufficient for M4B calibration. **Recommendation for M5 expansion:** Add a *Regulatory/Policy Shock* fixture (regulatory change that temporarily impairs a quality business without structural damage) and a *Commodity Trap* fixture (low-cost producer in a permanently declining commodity industry — the inverse of FIX-006).

## 8. Red Team + Audit Failure Paths Covered

**Finding: ✅ PARTIALLY COVERED — AUDIT PATHS SPECIFIED, RED TEAM NEEDS TIGHTENING**

**Audit paths (Acceptance Matrix §4):**

| Metric | Audit Method |
|--------|-------------|
| 4.2 Provenance Completeness | Automated check |
| 4.3 Failure-State Correctness | Curator audit |
| 4.4 Research-Stop Quality | Curator audit |
| 4.5 Audit-Gate Correctness | Curator checks audit gate log |
| 4.6 Report Factual-Error Rate | Post-publication audit, 100% fact-check |

**Red Team paths (implicit in fixture design):**

| Red Team Attack | Fixture That Tests It |
|----------------|----------------------|
| System over-relies on narrative → ignores fundamentals | FIX-010 (Narrative Panic) |
| System cannot detect fraud → accepts false quality | FIX-004 (False Quality) |
| System confuses industry cycle with company quality | FIX-006 (Industry Shock) |
| System cannot segment mixed cases → binary verdict | FIX-003 (Mixed Impairment) |
| System forces verdict on ambiguous evidence | FIX-008 (Ambiguous) |
| System ignores balance-sheet risk | FIX-005 (Balance-Sheet Trap) |
| System over-panics on company-specific shock | FIX-007 (Company Shock) |

**Gaps identified:**
1. **No explicit Red Team execution protocol.** The Evaluation Contract defines audit gates (4.5) but does not have a standalone Red Team section with adversarial test cases, injection attacks, or manipulation scenarios. **Recommendation:** Add a Red Team appendix to the Calibration Report specifying adversarial scenarios — e.g., poisoned evidence injection, temporal boundary edge cases, prompt-injection-resistance tests.
2. **No regression testing on known failure modes.** Once a system fails a fixture, there is no protocol to verify the fix and re-test. Without this, the same failure mode could recur in future evaluations.
3. **No blind evaluation protocol.** The curator evaluating the system's output may know the expected labels. A blind review (curator does not see expected labels when scoring output) would reduce confirmation bias.

## 9. Failure / Incomplete States Covered

**Finding: ✅ COVERED**

**Explicit failure/incomplete state handling:**

| Mechanism | Location | Detail |
|-----------|----------|--------|
| UNRESOLVED quality state | Fixture spec (FIX-008) | System explicitly assigned UNRESOLVED for ambiguous case |
| Failure-State Correctness metric | Acceptance Matrix §4.3 | *"% of fixtures where the system explicitly records failure states"* — tests FIX-008, FIX-003, FIX-004 |
| Research-Stop Quality metric | Acceptance Matrix §4.4 | Requires documented reason for stopping: saturation / sufficient evidence / information value below threshold / no more data |
| PIT Lock HARD BLOCK | Evaluation Contract §2.2 | Post-AS_OF evidence raises error — explicit failure state |
| INVALIDATE SEAL | pit-leakage-proof.py TEST 7 | Hash mutation triggers seal invalidation |
| AUDIT_GATE pass/fail | Acceptance Matrix §4.5 | Each gate must show explicit pass/fail |
| Threshold placeholder | Acceptance Matrix (all) | PROVISIONAL_M4B_THRESHOLD signals that thresholds are not yet calibrated |

**Gaps:**
- **No explicit "insufficient data" state** for when a fixture's pre-AS_OF evidence base is too thin for a meaningful verdict. The closest is UNRESOLVED, but UNRESOLVED implies "evidence supports both sides" not "evidence is insufficient."
- **No timeout/abort failure mode.** If a system takes too long on a fixture (e.g., 10x the median evaluation time), there is no defined abort-and-record-failure protocol.
- **No "system crash / service unavailable" state.** The Acceptance Matrix assumes successful execution; there is no defined behavior for partial evaluation due to system failure.

**Recommendation:** Add a `NOT_EVALUATED` outcome state for fixtures where the system aborts, times out, or encounters data insufficiency, with the evaluation report recording the reason.

## 10. Cost / Model Authority Restrictions Preserved

**Finding: ✅ PRESERVED AND STRUCTURED**

**4-tier model architecture (Evaluation Contract §7.1):**

```
Tier A — Bulk / cheap / free where reversible
Tier B — Operational
Tier C — Decision-critical
Tier D — Independent frontier challenge
```

**Authority restrictions (Evaluation Contract §7.2):**
> *"Cheap/free models may NOT be sole authority for:*
> - *Quality assessment*
> - *Moat classification*
> - *Impairment diagnosis*
> - *Normalized earnings*
> - *Permanent loss*
> - *Valuation asymmetry*
> - *Final underwriting*
> - *Final Red Team adjudication"*

**Assessment:**
- The 8 restricted domains cover all high-stakes analytical outputs. No cheap/free model can be the sole authority for any decision that affects a verdict or recommendation.
- The Acceptable Matrix §7 (Cost / Model Routing) has 6 metrics covering:
  - Cost per completed case
  - Tokens per stage
  - Expensive-model escalation rate
  - Retry cost
  - Deep Research cost
  - Decision-Changing Evidence per research cost (efficiency)
- These metrics are sufficient to determine whether cost routing is effective.
- **All authority-restricted domains have corresponding metrics** in the Acceptance Matrix: Quality assessment → 2.2, 2.3; Moat classification → implicit in 2.4 (impairment diagnosis); Normalized earnings → 3.2; Permanent loss → 3.3; Valuation asymmetry → 3.4, 3.5; Final underwriting → 2.6, 2.7; Final Red Team → implicit in failure-state coverage.

**Note:** The Evaluation Contract does not specify who or what constitutes a "Tier D" model. If Tier D models also have restricted domains, the current authority restrictions only apply to "cheap/free" (Tier A). This should be clarified in the Calibration Report.

**Finding: ✅ ALL HIDDEN THRESHOLDS REMOVED — VERIFIED**
